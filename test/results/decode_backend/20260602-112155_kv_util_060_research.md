# KV Cache GPU Memory Utilization Probe: 0.60

Date: 2026-06-02

## Setup

- Backend: full Triton dual-storage (`AWQ_MMQ_DECODE_BACKEND=triton`, `AWQ_MMQ_DECODE_POLICY=all`)
- Baseline: `.env` default `VLLM_GPU_MEMORY_UTIL=0.55`
- Probe: one restart with `VLLM_GPU_MEMORY_UTIL=0.60`
- Workload validation: one short `/v1/completions` request with proxy disabled

## Startup Capacity

| Config | gpu util | model GiB | KV available GiB | KV tokens | max concurrency |
|---|---:|---:|---:|---:|---:|

| gpu_util_0.60_full_triton | 0.60 | 40.50 | 26.41 | 91,520 | 3.43x |

Raising util from 0.55 to 0.60 adds 5.80 GiB available KV memory and 19,968 KV tokens (27.9%). Max 65,536-token concurrency rises from 2.68x to 3.43x.

## Interpretation

`VLLM_GPU_MEMORY_UTIL=0.60` is a promising memory-only knob: it gives nearly the same KV capacity gain as excluding the largest K-major shape, while keeping full Triton decode storage intact. This is likely a better first choice than dropping K-major layers when the goal is long-context capacity without short/mid throughput regression.

Caveat: this is not yet a full benchmark. It passed startup and one first-request probe, but the compose comment says first real GDN/Triton autotuning can need headroom. Before making 0.60 the default, run the standard short/mid/long benchmark and at least one long-context request after a cold restart.

The KV padding warnings remain unchanged: 4.17% and 25.00% possible waste in different layer groups. Page/block geometry is still worth studying because it may recover memory without reducing backend performance.
